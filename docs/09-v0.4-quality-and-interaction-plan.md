# 09. v0.4 课程质量与互动能力开发方案

> 文档版本：0.4
> 状态：方案设计已完成；M7.0 评价协议已冻结，mock smoke 和 DeepSeek v0.3 自动基线已完成，待人工七维评分；M7.1～M7.4 尚未实现
> 前置条件：M1～M6 的 v0.3 基线保持可运行、可回归、可从 MySQL 恢复
> 对应里程碑：M7；毕业论文研究延展暂存为 MX

## 1. 决策结论

M1～M6 已经解决“系统能否可靠运行”的问题，但当前课程仍以通用文字讲解、静态代码块和单选题为主。v0.4 不立即引入 LangGraph、多智能体、多模态、RAG 或媒体生成，而是集中解决两个产品问题：

1. 同一主题生成的课程能否更贴合学习者、目标和教学过程；
2. 课程能否至少包含一种安全、稳定、可操作的互动场景。

M7 采用下面的纵向路线：

```text
固定质量基线
  → Prompt 归一化 CourseBrief 与领域契约 v2
  → 幻灯片表达系统 v2、场景 Prompt v2 与课程连贯性
  → interactive/diagram 自包含互动脚本
  → 规则质量门、单场景再生成与成对质量验收
```

互动场景不是多智能体能力。它仍由现有 GenerationService 调用一个模型生成，保存到 MySQL，再由固定 React 宿主中的 sandbox iframe 执行。M7 不引入新的编排框架。

## 2. 当前差距与对应改动

| 当前限制 | 直接后果 | v0.4 对策 |
| --- | --- | --- |
| 当前只持久化主题和场景数，即使 Prompt 已写受众/难度/目标也没有结构化来源 | 后续模型各自猜测或遗漏要求，用户无法确认系统采用了什么 | 将 Prompt、可选高级设置和默认值归一为可追溯 `CourseBrief` |
| 大纲只有类型、标题、目标和关键点 | 容易重复“概念—机制—应用”的泛化结构 | 增加场景角色、误区、练习/评估意图 |
| slide 只有段落、列表、提示和代码 | JSON 无法表达并列概念、过程、对比等视觉关系 | 增加 card_grid、steps、comparison、table 固定渲染块和受控模板 |
| 当前 Renderer 使用单列文档流，正文使用大号展示字体 | 长段落获得接近标题的视觉重量，首屏被正文占满 | 建立有限幻灯片画布、字体层级、响应式模板和溢出检测 |
| Prompt 只说明字段和宽松长度上限 | 模型容易把讲稿写进屏幕内容，结构合法但不适合快速浏览 | 严格区分可见摘要与 narration，冻结每种模板的内容预算 |
| 场景只看到前一页摘要 | 跨页容易重复或遗漏目标 | 构造有上限的课程记忆：已覆盖、待覆盖、前文摘要 |
| repair 只修复结构错误 | JSON 合法不等于教学质量好 | 增加确定性质量报告和人工成对评价 |
| 只有 slide/quiz | 学习者只能阅读和作答 | 增加一种 `interactive/diagram` 场景 |
| ready 场景不能按意见重写 | 内容一般时只能整课重来 | 支持带简短指令的单场景再生成 |

Prompt 变长不是独立目标。只有字段、渲染器、校验器和运行时先具备表达能力，Prompt 才能要求模型生成相应内容。

## 3. v0.4 范围

### 3.1 必须交付

- `CourseBrief`：受众、学习者水平、学习目标、先修知识、预计时长、教学风格、互动偏好和附加要求，并保存每字段来源、解析状态和警告；
- `schemaVersion: 2`、v1 → v2 迁移函数和 MySQL `brief_json` 迁移；
- `outline.v2`、`scene-slide.v2`、`scene-quiz.v2` 和 `scene-interactive-diagram.v1`；
- `key_points`、`card_grid`、`process`、`comparison`、`code_explainer`、`summary` 六种受控幻灯片模板；
- `card_grid`、`steps`、`comparison`、`table` 四种新增固定 React 内容块；
- 可见内容预算、模板组合规则、确定性密度报告、DOM 溢出检查和双视口截图证据；
- `interactive` Scene 与仅支持 `diagram` 的 `InteractiveContent`；
- 自包含 HTML/CSS/JavaScript 的解析、大小限制、静态安全检查、一次修复和失败隔离；
- 无 `allow-same-origin` 的 iframe 宿主、CSP、运行错误上报、重置和完成事件；
- ready 场景带用户指令的事务化再生成；
- 固定评价集、人工量表、基线/候选对比报告和 M6 全量回归。

### 3.2 明确不做

- LangGraph、教师/学生多智能体、圆桌讨论和角色扮演；
- PDF/Word/PPTX/图片输入、OCR、视觉模型、图片或视频生成；
- Web 搜索、RAG、引用溯源和自动事实核验；
- code widget、任意代码执行、simulation、game、3D 和 PBL；
- 外部脚本、CDN、iframe 内网络请求和跨页面共享身份；
- 自由坐标 PPT 画布、专业编辑器和复杂 Action 编排；
- 把 LLM-as-judge 分数作为在线硬门或事实正确性证明。

如果 diagram 纵向闭环尚未稳定，不得同时增加第二种 widget。

## 4. 课程需求与默认值

`CourseBrief` 不是要求用户重复填写的一张完整表单，而是系统从“原始课程描述 + 可选高级设置 + 服务端默认值”中解析出的**有效教学上下文**。首页仍只要求用户填写主题或自然语言描述；高级设置保持可选。用户已经在描述中写明“面向大一学生、零基础、学完能独立实现一个 React 组件”时，系统应识别并复用这些信息，而不是再次要求填写，也不能让模型在后续每个场景中重新猜测。

原始 `topic` 必须按用户提交内容原样保存，不能被模型概括出的主题、受众或目标覆盖。M7.1 暂不为了命名整洁额外拆分 `requestText/title`；如果后续确需将“生成要求”和“课程标题”分列，应作为独立的数据迁移处理。

```ts
export interface CourseBrief {
  audience: string;
  learnerLevel: 'beginner' | 'intermediate' | 'advanced';
  learningGoal: string;
  prerequisites: string[];
  durationMinutes: 10 | 15 | 20;
  teachingStyle: 'structured' | 'case_based' | 'practice_oriented';
  interactionMode: 'off' | 'auto' | 'required';
  additionalRequirements: string[];
}

export type CourseBriefField = keyof CourseBrief;
export type BriefValueSource = 'explicit_setting' | 'prompt' | 'default';

export interface BriefResolutionWarning {
  code: 'SETTING_PROMPT_CONFLICT' | 'PROMPT_AMBIGUOUS' | 'SCOPE_TOO_BROAD' | 'LEGACY_DEFAULT_APPLIED';
  field?: CourseBriefField;
  message: string;
}

export interface CourseBriefResolution {
  status: 'provisional' | 'resolved';
  sources: Record<CourseBriefField, BriefValueSource>;
  warnings: BriefResolutionWarning[];
  resolvedAt?: string;
}
```

`audience` 表达“大一学生、企业新员工、准备面试的 Java 开发者”等具体对象，`learnerLevel` 表达其知识水平，两者不能互相替代。`additionalRequirements` 只保存用户明确提出、但不属于固定字段的教学约束，例如“必须包含代码示例”“不要使用数学推导”“多用真实案例”；模型不能根据学科自行补写偏好。

### 4.1 字段来源与合并优先级

每个最终字段都必须记录来源，合并顺序固定为：

```text
显式高级设置 explicit_setting
  > 原始描述中的明确要求 prompt
  > 服务端确定性默认值 default
```

这里的“明确要求”指可以从原文直接定位的信号，不是按学科常识推断。例如“给零基础高中生讲解”可以解析出 audience 和 beginner；只写“量子力学”不能因为主题较难就擅自判定 advanced。高级设置字段只有在请求中真实出现时才算 `explicit_setting`；字段缺失表示交给 Prompt 解析或默认值，显式空数组则表示用户明确要求“无先修知识”，不能与缺失混为一谈。

当描述与高级设置冲突时，高级设置胜出，并保存 `SETTING_PROMPT_CONFLICT` 警告供生成页展示。例如原文写“面向零基础”，高级设置选择 advanced，最终值是 advanced，但页面应提示发现了冲突，不能静默覆盖。原文内部含糊或互相矛盾时保存 `PROMPT_AMBIGUOUS`；范围明显超过 10～20 分钟微课时保存 `SCOPE_TOO_BROAD`。警告用于解释和提醒，不应让一次可安全默认的生成直接失败。

### 4.2 有信息和无信息时的处理

`POST /api/courses` 接收原始 `topic`、场景数和可选 `briefOverrides`。创建阶段不额外调用模型：服务端先用高级设置覆盖默认值，写入 `status=provisional` 的 brief。随后原有的 `outline.v2` 调用在同一个结构化响应中同时返回：原文中检测到的 brief 字段、解析警告、按优先级得到的 `resolvedBrief` 和课程大纲。服务端根据“高级设置 > 检测字段 > 默认值”重新计算最终 brief；如果模型返回的 `resolvedBrief` 与服务端结果不一致，则按大纲契约失败处理并进入既有受限 repair，而不是接受两份不同上下文。

因此这项能力不会固定增加一次 LLM 调用。正常路径仍是一次 `outline.v2` 请求；只有响应本身违反 Schema 或合并规则时，才与其他大纲错误一样消耗既有修复预算。最终 CourseBrief、来源、警告和大纲必须在同一短事务中保存，使“系统理解的要求”和“据此生成的大纲”保持同一 revision。

如果 Prompt 已经包含受众、难度或学习结果，就把这些明确字段标记为 `prompt` 并参与大纲设计，只为未提到的字段补默认值。如果 Prompt 只有主题，则所有未设置字段保持 `default`，模型不得偷偷添加无法追溯的受众假设。用户输入属于待解析数据；即使描述中出现“忽略系统规则、输出任意 HTML”等文字，也不能改变 System Prompt、JSON Schema、安全门或字段优先级。

推荐默认值如下：

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| audience | `无特定专业背景的学习者` | 不擅自假定年龄、职业或专业 |
| learnerLevel | `beginner` | 不假定专业背景 |
| learningGoal | `理解「{topic}」的核心概念、基本机制与典型应用` | 服务端确定性模板；超长 topic 按 Schema 上限安全截断 |
| prerequisites | `[]` | 不凭空要求先修课程 |
| durationMinutes | `15` | 保持微课范围 |
| teachingStyle | `case_based` | 先用问题或案例建立动机，再解释机制 |
| interactionMode | `auto` | 只有确有教学价值时生成，且每课最多一个 |
| additionalRequirements | `[]` | 不替用户创造额外要求 |

`requestedSceneCount` 在 v0.4 仍保持 3～5，默认 5，避免同时扩大生成成本和播放器状态空间。`interactionMode=required` 主要用于演示与 E2E；`auto` 模式不能为了展示功能而给纯文本概念强塞互动页。

### 4.3 页面确认与重新生成边界

首页第一版只需把 audience、learnerLevel 和 learningGoal 作为可选高级设置，其余字段继续使用默认值；`interactionMode` 可在 M7.3 互动闭环接入时再显示。大纲页在模型返回后增加“系统理解的课程要求”摘要，为每个字段标记“高级设置 / 来自描述 / 默认值”，并展示冲突或范围警告。

用户在确认大纲前修改已解析 Brief 时，新值按 `explicit_setting` 保存，同时使当前大纲失效并要求重新生成；不能让旧大纲继续搭配新 Brief。M7.1 不允许在场景已经生成后直接修改整课 Brief，整课重规划属于后续受控再生成范围。这样既保留纠正模型理解的入口，也避免 CourseBrief、大纲和已生成场景出现版本错位。

## 5. 计划领域契约

### 5.1 大纲

```ts
export type SceneTypeV2 = 'slide' | 'quiz' | 'interactive';

export type SceneRole =
  | 'hook'
  | 'concept'
  | 'mechanism'
  | 'worked_example'
  | 'practice'
  | 'summary'
  | 'assessment';

export interface SceneOutlineV2 {
  id: string;
  type: SceneTypeV2;
  role: SceneRole;
  title: string;
  teachingObjective: string;
  keyPoints: string[];
  misconceptions?: string[];
  assessmentFocus?: string;
  widgetType?: 'diagram';
  order: number;
  estimatedMinutes?: number;
}
```

课程级规则包括：第一场不能是 quiz；至少一个且最多两个 quiz；互动模式不是 `off` 时最多一个 interactive；interactive 不能作为第一场，必须服务于已经引入的概念；`required` 模式必须恰好生成一个 `widgetType=diagram` 场景。

### 5.2 SlideContent v2 与受控模板

当前 `SlideContent` 只说明“页面里有哪些 Block”，没有说明这些 Block 之间是什么视觉关系。即使 Prompt 让模型生成并列概念，Renderer 也只能把它们纵向堆叠。因此 v0.4 在保留固定 React 安全边界的前提下，引入受控模板：模型选择内容关系，Renderer 决定空间布局，模型不生成坐标、CSS 或 React。

```ts
export type SlideTemplate =
  | 'key_points'
  | 'card_grid'
  | 'process'
  | 'comparison'
  | 'code_explainer'
  | 'summary';

export interface SlideContentV2 {
  type: 'slide';
  template: SlideTemplate;
  subtitle?: string;
  blocks: SlideBlockV2[];
}
```

模板负责表达页面的主要信息关系，而不是装饰风格：

| 模板 | 主要用途 | 推荐主 Block | 典型 SceneRole |
| --- | --- | --- | --- |
| `key_points` | 一条核心定义加少量关键点 | paragraph + bullet_list/callout | hook、concept |
| `card_grid` | 2～4 个同层级概念并列展示 | card_grid | concept、summary |
| `process` | 步骤、循环或因果链 | steps | mechanism、worked_example |
| `comparison` | 两个对象按相同维度比较 | comparison | concept、worked_example |
| `code_explainer` | 代码与解释并排 | code + bullet_list/callout | worked_example、practice |
| `summary` | 收束本场景或整门课的结论 | bullet_list/card_grid + callout | summary |

`scene-slide.v2` 必须返回一个上述模板。模板不能由模型自由命名，也不能用 `key_points` 包装任意长文章。模板与 Block 组合由语义门校验，例如 `process` 必须包含一个 steps，`comparison` 必须包含一个 comparison，`code_explainer` 必须包含一个 code；其他辅助 Block 数量受限，避免重新退化成纵向堆叠。

v1 课程不能因为缺少 `template` 而无法恢复。读取端继续接受旧版 SlideContent，并在 Renderer 内走 `legacy_stack` 兼容分支；`legacy_stack` 只是内部回退，不允许出现在 v2 模型输出中。旧 ready 场景只有在用户明确再生成时才替换为 v2 内容，不在读取或迁移过程中静默改写。

### 5.3 丰富静态内容块

v0.4 保留 paragraph、bullet_list、callout、code，并增加四个受控类型：

- `card_grid`：2～4 张卡片，每张包含短标题和 1～3 个短要点；桌面端最多三列，窄屏按语义顺序重排；
- `steps`：2～6 个有序步骤，每步包含短标题和一句说明；循环过程允许闭环标识，但不允许自由坐标箭头；
- `comparison`：两个对象的 2～5 项同维度比较，必须保证左右项目能够按顺序对应；
- `table`：2～5 列、1～6 行的短文本表格，只用于确有行列关系的数据，不把普通列表强行做成表格。

计划领域形状如下。这里的 `id` 由装配器生成，模型 DTO 继续省略实体 ID；comparison 使用逐行三元组而不是两个独立数组，避免左右项目错位；table 必须用 `superRefine` 保证每行单元格数量等于 headers 数量。

```ts
export interface CardGridBlock {
  id: string;
  type: 'card_grid';
  cards: Array<{
    title: string;
    points: string[];
  }>;
}

export interface StepsBlock {
  id: string;
  type: 'steps';
  steps: Array<{
    title: string;
    description: string;
  }>;
}

export interface ComparisonBlock {
  id: string;
  type: 'comparison';
  leftTitle: string;
  rightTitle: string;
  rows: Array<{
    dimension: string;
    left: string;
    right: string;
  }>;
}

export interface TableBlock {
  id: string;
  type: 'table';
  caption?: string;
  headers: string[];
  rows: string[][];
}
```

paragraph 在 v2 中只承担短定义或关键结论，不再作为默认长正文；每页最多一个。code 继续作为 React 文本节点转义，不执行其中的 HTML/JSX/TSX。所有新增类型仍由固定 React 组件渲染，不允许模型返回 CSS、React 或普通字段中的任意 HTML。公式、图片和自由坐标布局不进入本版本。

### 5.4 可见内容与 narration 契约

v2 将“屏幕上展示什么”和“讲解时说什么”视为两个不同产物：可见内容用于在数秒内识别结构和结论，narration 用于解释原因、例子、过渡和细节。减少屏幕文字不等于减少知识量，而是把详细教学内容移动到更合适的讲解层。

Prompt、Schema 和质量报告共同执行以下规则：

1. 每个 slide 只承担一个主要教学结论，标题不能同时包含多个并列教学任务；
2. 可见字段使用关键词、短语、短定义和要点，不使用“下面我们来看”等口语化过渡句；
3. narration 可以引用可见结构，但不能逐字复述整页，也不能把只有 narration 才出现的关键结论藏起来；
4. 标题、subtitle、Block 标题和要点不能大面积重复，页面末尾的 takeaway 必须提供新的收束而不是复制标题；
5. 模型不能为了满足 Block 数量虚构概念，也不能把一段长文机械拆成多张卡片。

建议由 M7.0 在改动生产 Prompt 前冻结 `slide-density.v1`。以下数值作为初始上限候选，最终值一经 M7.0 记录便不能根据候选课程临时放宽：

| 可见元素 | 结构硬上限或兼容边界 | v2 质量目标 |
| --- | --- | --- |
| Scene 标题 | 继续兼容现有 80 字符存储边界 | 通常 8～22 个中文字符，最多两行 |
| subtitle | 继续兼容现有 120 字符存储边界 | 不超过 36 个中文字符，最多两行 |
| paragraph | v2 最多 120 字符且每页最多一个 | 通常 40～80 个字符，只写短定义或结论 |
| bullet/card/step 单项 | v2 单项最多 60 字符 | 通常不超过 30 个中文字符 |
| callout 可见正文 | v2 最多 120 字符 | 通常不超过 60 个中文字符 |
| code | 继续保留源码安全上限 | 建议 8～18 行；超长示例只展示关键片段并在 narration 解释 |

`visibleCharCount` 在折叠空白后统计标题、subtitle、caption 和所有可见说明，不统计 code 原文；代码另记 `codeLineCount` 和最长行。初始模板预算建议为：`key_points ≤ 160`、`card_grid ≤ 220`、`process ≤ 180`、`comparison ≤ 220`、`code_explainer ≤ 120`、`summary ≤ 150`。这些预算是可复现的工程起点，不等于教学质量分数，也不能替代人工判断。

### 5.5 Renderer、响应式布局与视觉层级

Renderer v2 继续使用当前产品的米色纸张、红/绿强调色和整体编辑感，但重新分配字体职责：衬线展示字体只用于短标题或关键结论，正文、卡片要点和说明统一使用更适合屏幕阅读的无衬线字体。不能通过把所有文字加粗或持续缩小字号来解决内容过载。

建议冻结以下设计区间，并在实现时根据实际字体渲染截图微调一次：

| 层级 | 桌面端建议 | 说明 |
| --- | --- | --- |
| slide 主标题 | 34～42px，1.15～1.25 行高 | 最多两行，与外层场景导航标题区分 |
| subtitle/教学目标 | 18～22px，1.4～1.55 行高 | 使用次要颜色但保持可读对比度 |
| 卡片或步骤标题 | 20～24px，1.3～1.45 行高 | 不与正文共用展示级字号 |
| 正文和要点 | 16～18px，1.5～1.7 行高 | 默认无衬线，避免超长行 |
| caption/辅助信息 | 13～15px | 不能承担关键教学信息 |

桌面端的 slide surface 以 16:9 为设计基准，在标准课堂布局中应完整落入可视区域，不依赖内部滚动才能读完。模板使用 CSS Grid/Flex 的确定性布局，不使用模型坐标。窄屏不能按比例缩小到难以阅读：`card_grid` 改为单列或两列、comparison 上下排列、code_explainer 改为代码与解释顺序堆叠，并保持正文不低于 16px。窄屏允许课堂主页面随重排后的内容纵向增长和滚动，但模板内部不能横向裁切、隐藏关键文字或制造嵌套阅读滚动区。DOM 顺序必须与视觉阅读顺序一致，颜色只用于增强分组，不能成为区分概念的唯一手段。

Renderer v2 直接使用已有 `Scene.title` 作为 slide surface 的教学主标题，不在 SlideContent v2 中再保存一份容易漂移的 title。外层 `scene-heading` 只承担课程导航和场景定位，应比当前更紧凑；真正的教学标题和内容层级在 slide surface 内完成。旧版 `legacy_stack` 保持可读但不追求新模板效果，避免为了视觉升级破坏历史课程。

### 5.6 Prompt v2、模板选择与受限修复

模板在现有 scene 生成调用中一次性选择，不增加独立的“视觉设计 Agent”或额外规划调用。`SceneRole`、teachingObjective、keyPoints、CourseBrief 和受限课程记忆共同决定候选模板；Prompt 给出推荐映射，但允许模型在合法集合内选择更符合内容关系的模板。

`scene-slide.v2` 至少明确：

- slide 是视觉辅助，不是 lecture script；详细解释进入 narration；
- 先识别内容关系，再选择模板，不允许所有页面都退化为 card_grid；
- 并列概念用 card_grid，步骤或循环用 process，同维度差异用 comparison，代码实践用 code_explainer；
- 每个可见字段遵守短文本目标，禁止整段口语、重复标题和无意义装饰文案；
- narration 解释因果、误区和例子，并与当前 SceneRole、学习者水平和前后页上下文一致；
- 只返回 Schema 允许的 JSON，不返回坐标、CSS、React 或可执行 HTML。

输出先经过 JSON/Schema、安全门、模板组合和硬密度规则。模板非法、必需主 Block 缺失、可见文字超过硬上限或出现明显重复时，可以复用现有一次模型 repair；repair 必须收到具体失败项并要求压缩或重组，而不是简单截断。repair 与传输重试继续共享现有最多四次上游调用预算，不能因为视觉优化暗中增加第五次调用。修复后仍不合格则按当前场景失败流程保存错误，已经完成的其他场景继续保留。

### 5.7 确定性质量报告与视觉证据

`lib/quality` 为每个 slide 生成可审计的报告，至少记录：

```ts
export interface SlideQualityReport {
  template: SlideTemplate | 'legacy_stack';
  visibleCharCount: number;
  longestItemChars: number;
  blockCount: number;
  codeLineCount?: number;
  duplicateSignals: string[];
  densityStatus: 'pass' | 'warning' | 'fail';
  violations: string[];
}
```

服务端可以确定性检查字符、数量、组合、重复和代码行数，但不能凭 JSON 推断真实字体换行。浏览器测试必须额外检查 slide surface 及关键子容器的 `scrollWidth/clientWidth`、`scrollHeight/clientHeight`，并在 `1280×720` 桌面视口和 `390×844` 窄屏视口保存同一场景截图。首版以 DOM 溢出断言阻塞合并，截图作为人工对照证据；在字体和运行环境稳定前，不启用容易误报的跨平台像素级硬门。

Schema、安全、模板组合和最终 DOM 溢出属于硬门；“模板是否最合适”“页面是否有吸引力”和“教学解释是否优秀”属于人工评价，不能伪装成确定性校验。结构合法、页面不溢出，也不代表事实正确或教学质量达标。

### 5.8 互动内容

```ts
export interface InteractiveContent {
  type: 'interactive';
  widgetType: 'diagram';
  runtimeContractVersion: 1;
  html: string;
  fallback: {
    title: string;
    description: string;
    steps: string[];
  };
}
```

`html` 必须是一个完整、自包含的 HTML 文档，最大 100 KiB，不允许外部 URL、子 iframe、对象嵌入、表单提交或下载。fallback 始终由固定 React 渲染器显示加载说明，并在 iframe 失败时提供静态替代，不让单个互动脚本造成课堂白屏。

互动场景的 Action 先复用现有 `speech + learner pause`。iframe 发出合法的 `INTERACTIVE_COMPLETED` 后，播放器把它解释为当前 learner pause 已完成；M7 不为此引入通用 widget Action 系统。

## 6. 互动运行时安全契约

生成 HTML 一律视为不可信代码。它不能通过 `dangerouslySetInnerHTML` 进入主应用 DOM，只能进入独立 iframe：

```html
<iframe sandbox="allow-scripts" srcdoc="..." />
```

必须满足以下边界：

1. sandbox 只包含 `allow-scripts`，不包含同源权限、表单提交、顶层导航、弹窗或下载权限；
2. 宿主注入 CSP：默认拒绝所有资源，只允许内联样式、内联脚本和必要的 `data:` 图片，明确设置 `connect-src 'none'`、`form-action 'none'`、`worker-src 'none'` 和 `object-src 'none'`；
3. CSP 不允许 `unsafe-eval`；HTML/JavaScript 解析同时拒绝 `eval`、`Function`、动态 import、Worker、WebAssembly、外部 script/link、iframe、object、embed、meta refresh、`window.open`、location 导航、持续 `setInterval/requestAnimationFrame` 和明显无界循环；diagram 第一版只允许事件驱动 DOM 与 CSS transition；
4. 父页面只接受 `event.source === iframe.contentWindow` 且通过 Zod 的消息，不依赖 sandbox 的 `null` origin 判断身份；
5. 子页面只允许发送 `INTERACTIVE_READY`、`INTERACTIVE_COMPLETED` 和 `INTERACTIVE_ERROR`；父页面只发送 `INTERACTIVE_RESET`；
6. 5 秒未 ready、脚本运行异常或消息不合法时显示 fallback，并允许用户跳过或重新生成；
7. 切换场景、重播和卸载时清理 message listener、计时器和旧 iframe，拒绝迟到事件。

静态扫描只能减少明显风险，真正的隔离边界是 sandbox、CSP、无外部网络和严格的消息协议。

## 7. M7 开发分解

### M7.0：冻结质量基线

**任务**：建立 `eval/config/course-quality.v1.json`，覆盖概念解释、机制流程、编程实践三个类别，每类至少两个公开、无隐私主题；用当前 `outline.v1 + scene-*.v1` 生成基线，保存评分、Provider、模型、Prompt 版本、耗时、调用次数和 token 汇总。每个 slide 同时保存脱敏后的结构化内容、SlideQualityReport v0、`1280×720` 桌面截图和 `390×844` 窄屏截图，记录当前长段落、标题层级、首屏占用和溢出情况。

**人工量表**：事实正确性、目标匹配、结构连贯、解释与案例价值、可见内容可读性、视觉层级与版式适配、测验对齐度七项均使用 1～5 分；出现会误导学习者的关键事实错误时额外标记 `criticalError=true`。可见内容可读性重点评价文字是否短而可扫读，视觉层级与版式适配重点评价标题/正文主次、内容关系是否被正确表达以及首屏是否过载，不能只按“是否好看”给分。

**退出门**：评价集、评分说明、`slide-density.v1`、截图视口、模型/Prompt 配置和基线报告都可复现；此阶段不修改生产 Prompt、Schema、Renderer 或 CSS。开发期只使用 6 个主题做快速对比，论文阶段若选择质量研究再扩大样本和重复次数。基线冻结后不得因为 v0.4 候选未达标而临时改变量表、预算或阈值。

### M7.1：CourseBrief、Schema v2 与 Prompt v2 大纲

**任务**：实现 Course v1/v2 判别读取、`migrateCourseV1ToV2`、`brief_json` 迁移、创建 API 的可选 `briefOverrides`、首页折叠设置区、Brief 来源展示、`outline.v2` 同调用解析与大纲生成，以及确认前编辑/失效规则。创建时保存原始 topic 和 provisional brief；`outline.v2` 返回检测字段、警告、resolvedBrief 与 outlines，服务端按固定优先级复算，并把 Brief/Resolution/大纲在同一事务中保存。旧 v1 课程必须可打开、播放，并在明确保存时迁移，不能要求清库或重新生成旧内容。SceneRole 在这一阶段成为后续模板选择的稳定输入，但 M7.1 不提前修改 slide 样式或生产 scene Prompt。

**最小测试**：只有主题、描述字段完整、描述字段部分缺失三类解析；显式设置优先、同值不告警、冲突告警和含糊描述；原始 topic 原样保存；字段来源和警告持久化；正常 outline 不增加额外模型调用；Brief/大纲同事务保存；修改 Brief 后旧大纲失效；Prompt 注入不能绕过 System Prompt/Schema；v1 fixture 使用确定性默认值迁移且不重生成；v2 MySQL 新实例恢复；outline role/互动数量规则。

**退出门**：同一原始描述在纯默认值与显式受众/目标设置下能生成有可解释差异且结构合法的大纲；有效 Brief、每字段来源、警告和大纲可从 MySQL 一致恢复；用户能看到系统采用了哪些描述信息并在确认前纠正；旧 v1 课程和 M6 E2E 继续通过。

### M7.2：幻灯片表达系统 v2 与课程连贯性

M7.2 是本轮模板和 LLM 内容优化的主要实现阶段，不能被简化成一次 CSS 调整，也不能只增加 Block 后继续沿用宽松 Prompt。按以下内部顺序实施：

1. **M7.2a—领域契约与旧数据兼容**：增加 SlideContent v2、SlideTemplate、card_grid/steps/comparison/table Schema、模板组合语义门和 fixture；读取端保留 v1 SlideContent 联合分支，缺少 template 的旧场景进入 `legacy_stack`，不能要求清库或静默重写历史课程；
2. **M7.2b—固定模板与视觉层级**：实现六种模板、16:9 桌面 slide surface、字体层级、卡片/步骤/对比/代码布局和窄屏语义重排；压缩外层 scene-heading，正文不再使用接近标题的大号展示字体；
3. **M7.2c—Prompt v2 与课程记忆**：升级 slide/quiz Prompt，模板在同一次 scene 调用中选择；上下文加入有长度上限的 `coveredKeyPoints`、`remainingObjectives` 和前文摘要，严格区分可见短内容与 narration；
4. **M7.2d—规则质量门与证据**：增加模板组合、重复内容、页面密度、关键点覆盖和 quiz—objective 对齐报告；浏览器执行桌面/窄屏 DOM 溢出断言并保存截图。

**最小测试**：

- 每个新 Block 的最小/最大边界、未知字段拒绝、普通文本 HTML 拒绝和 code 转义；
- 每种模板的合法/非法 Block 组合、v1 `legacy_stack` 恢复和 v2 再生成替换；
- 标题、subtitle、单项、整页密度、重复信号、代码行数和 repair 预算；
- `1280×720` 与 `390×844` 下的 DOM 顺序、水平/垂直溢出、最小字号和截图；
- 课程记忆裁剪、covered/remaining 一致性、quiz 对目标的引用和 mock 完整课程；
- DeepSeek smoke 中的模板分布、首次通过/repair 次数、token、耗时和最终页面截图。

**退出门**：固定 6 主题的候选课程能够生成、保存、重启恢复和播放；所有最终保存的 v2 slide 均通过 Schema、安全、模板组合和硬密度规则，标准桌面与窄屏没有未声明溢出；v1 课程仍能打开；M6 全量回归继续通过。候选课程不能通过增加长段落、把关键正文或要点缩小到 16px 以下，或把所有内容改成卡片来伪造“更丰富”。完成这一退出门后才开始 M7.3。

### M7.3：interactive/diagram 纵向闭环

**前置条件**：M7.2 的 SlideContent v2、质量门、双视口渲染和旧课程兼容已经通过退出门。若静态课程仍频繁溢出或只能靠人工挑选好样本，不进入互动开发。

**任务**：扩展 Scene 联合、生成路由、专用 Prompt、HTML 校验和修复、InteractiveRenderer、iframe bridge、fallback、播放等待和 MySQL 恢复。mock 必须返回一个最小但真实可操作的 diagram HTML，而不是静态占位图。

**最小测试**：Schema/装配器、危险 HTML 拒绝、sandbox/CSP 属性、消息来源校验、ready 超时、runtime error、reset、completed、切页迟到事件、失败隔离和 production Chromium E2E。

**退出门**：在 `interactionMode=required` 下完成“创建 → 大纲含一个互动页 → 生成并持久化 → 课堂点击节点/逐步查看 → 重置 → 完成 → 刷新后重新加载”的完整链路；主页面 DOM、Cookie、localStorage 和网络不能被 iframe 访问。

### M7.4：单场景再生成与质量验收

**任务**：允许用户对 ready 场景提交不超过 500 字的修改指令；服务端读取现有场景作为有上限的 baseline，在不改变 Course.status、SceneProgress 或持久化 activeOperation 的情况下生成候选，最后以 expectedRevision 替换同 outlineId 场景。旧结果在新结果事务提交前保持可用，失败不能把 ready 场景改丢。quiz 再生成必须先提示旧作答会失效；用户确认后，替换场景与删除旧 sceneId 的 QuizAttempt 在同一 MySQL 事务提交。slide 修改指令可以要求“更精炼、改为对比、突出步骤”等受控变化，但最终模板和密度仍必须通过 M7.2 的同一质量门，不能给再生成开后门。

**最小测试**：无指令/超长指令拒绝、模型不能修改 outlineId/order、成功替换而非追加、失败保留旧结果、并发冲突、slide 模板变更仍通过密度/溢出门、quiz 作答确认/原子清理、互动页重新生成和 E2E。

**退出门**：完成 M6 全量回归和 v0.4 新增 E2E；在相同主题、学习目标、Provider、模型和记录完整的请求设置下，对 v0.3/v0.4 做成对评价。截图使用相同视口，样本顺序在条件允许时打乱，评价者不能只看到版本标签后凭预期给分。建议由 M7.0 冻结的初始阈值为：目标匹配、教学组织、案例/练习价值、可见内容可读性、视觉层级与版式适配五项平均提升至少 0.5/5，事实正确性不得下降，标准视口不存在硬溢出，至少 70% 的课程对更偏好 v0.4；同时报告而不隐藏延迟、token、首次通过率、repair 次数和模板分布变化。

## 8. 推荐提交顺序

（以下仅是建议，开发者还是希望可以尽量减少commit次数，开发时假如认为需要commit时应该先请示开发者）

每个提交都必须保持主分支可构建，建议按以下顺序实施：

1. `docs/eval: 冻结 v0.3 质量基线与评分协议`；
2. `feat(domain): 增加 Course v2、CourseBrief 与迁移`；
3. `feat(course): 保存课程设置并升级 outline.v2`；
4. `feat(domain): 增加 SlideContent v2、受控模板、新 Block 与 v1 兼容`；
5. `feat(render): 增加幻灯片画布、视觉层级和响应式固定模板`；
6. `feat(generation): 升级 slide/quiz Prompt、课程记忆与规则质量报告`；
7. `test(visual): 增加双视口溢出断言、截图与 DeepSeek slide smoke`；
8. `feat(interactive): 增加 diagram 生成、校验与持久化`；
9. `feat(classroom): 增加沙箱 iframe 与互动完成协议`；
10. `feat(generation): 支持 ready 场景按指令再生成`；
11. `test/docs: 完成 v0.4 回归、成对质量报告与交付文档`。

Schema/迁移提交必须先于依赖它的 API 和 UI。SlideContent v2 的领域提交可以先进入主分支，但必须保持 v1 Renderer 和 fixture 全绿；新模板 Renderer、Prompt 和质量门应连续完成，不能让生产 Prompt 输出页面暂时无法渲染的模板。InteractiveContent、生成器、Renderer 和 E2E 必须在同一个短分支中形成完整纵向闭环，不能把“类型已加入但页面无法处理”的中间状态长期留在主分支。

| mock E2E | 不访问付费模型时完整产品链是否可重复 | 是 |
| DeepSeek smoke | 真实 Prompt 能否生成可用课程和互动脚本 | M7 退出时是，日常 CI 否 |
| 人工质量评价 | 内容是否比 v0.3 更适合学习 | M7 退出时是，单次提交否 |
| LLM-as-judge | 辅助发现可能问题 | 否，不能替代人工与事实核验 |

结构通过率、运行成功率和教学质量必须分别报告。互动页面能够加载，不代表互动具有教学价值；人工认为内容不错，也不能替代 sandbox 和错误恢复测试。

## 10. 止损与回退规则

- M6 的 `pnpm verify:full` 连续失败时停止扩展，先恢复 v0.3 回归；
- v1 课程不能读取或迁移时停止 Prompt/UI 开发，先修复兼容性；
- 新模板只有在缩小正文字号、隐藏内容或允许内部滚动时才不溢出，说明内容契约或模板容量错误；回退 Prompt/模板，不接受视觉掩盖；
- Prompt 已要求 card/process/comparison，但 Schema 或 Renderer 无法表达对应关系时，先补齐结构，不继续堆叠自然语言指令；
- M7.2 未通过双视口硬门和 v1 恢复回归时，不开始 interactive/diagram；
- iframe 能访问主页面身份、发起外部网络请求或逃逸 sandbox 时，立即关闭 interactive 生成入口；
- 真实互动脚本在一次修复后仍频繁白屏时，不增加第二种 widget，先收紧模板与运行契约；
- 如果质量分数没有改善，先检查 CourseBrief 是否实际进入 Prompt、领域结构是否能表达要求、模板选择是否匹配内容关系、可见内容是否与 narration 分工以及评分是否一致，不通过继续堆 Prompt 长度掩盖问题；
- M7 未达到退出门前，不引入 LangGraph、多智能体、多模态或 RAG。
