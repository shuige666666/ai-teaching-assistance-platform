# 10. M6.5 远端响应韧性与可观测性开发方案

> 文档状态：已实施并验收（2026-08-26）
> 对应里程碑：M6.5；M6 保持已完成；后续 v0.4 计划已在本里程碑完成后重分为 M7～M10
> 适用边界：本机 + MySQL + mock + DeepSeek，不包含百炼联调和异机部署

## 1. 背景与目标

M6 已证明课程可以生成、增量保存、局部重试和从 MySQL 恢复，但真实 DeepSeek 调用暴露了一个更细的边界：上游可能返回 HTTP 2xx，但响应体为空、不是合法 JSON，或不符合预期的 OpenAI-compatible envelope。当前 `OpenAICompatibleAdapter` 把这些情况统一映射为不可重试的 `AI_UPSTREAM_ERROR`，前端因而显示“失败 / 需人工处理”，无法区分认证配置问题和偶发远端响应异常。

M6.5 不增加新课程能力，只加固现有 v0.3 生成闭环：

- 对 HTTP、网络、响应解码和模型内容校验失败分层归类；
- 对可恢复的空响应和偶发 envelope 异常执行受限自动重试；
- 使用户看到“正在重试 / 可手动重试 / 需修正配置”，开发者能用 `requestId` 定位失败阶段；
- 保留严格 Zod、一次模型 repair、局部失败隔离和调用硬上限。

M6.5 只证明远端调用的工程韧性，不把“能解析”宣称为事实正确或教学质量提升。

## 2. 与 OpenMAIC 的取舍

OpenMAIC 先由 AI SDK 将 Provider 响应归一化为文本，再在生成边界对空结果、临时 HTTP 错误和网络错误进行指数退避重试，并对模型 JSON 执行多步修复。本项目借鉴“响应层与内容层分开、空结果可受限重试”的做法，但不直接复制以下行为：

- 不引入新 AI SDK，继续使用小型 `AIAdapter` 边界；
- 不记录 Prompt、课程主题或原始模型响应；
- 不用宽松解析绕过 Zod 和领域语义门；
- 不将失败静默降级为 mock 或伪造成功场景。

## 3. 计划错误分类

### 3.1 HTTP 与连接层

| 类型 | 例子 | 计划行为 |
| --- | --- | --- |
| 配置/认证 | 缺 Key、401、403 | 不自动重试，提示修正服务端配置 |
| 请求不兼容 | 400、404、422 | 不反复重试，记录状态和阶段供开发者排查 |
| 限流/临时故障 | 408、425、429、5xx | 按现有策略最多自动重试 2 次 |
| 网络/超时 | 连接重置、DNS、timeout | 受 AbortSignal 和预算约束的自动重试 |
| 用户取消 | AbortError 且由客户端主动触发 | 立即停止，不发起新请求 |

### 3.2 HTTP 2xx 响应层

Adapter 先安全读取响应文本，再解析 JSON 和 envelope，避免 `response.json()` 将“空体、非 JSON、Schema 不匹配”折叠为同一个未知异常。内部诊断至少区分：

- `empty_body`：HTTP 2xx 但响应体为空；
- `invalid_json`：响应体不是合法 JSON；
- `invalid_envelope`：缺少可识别的 `choices/message/content` 结构；
- `empty_content`：envelope 合法，但模型文本为 `null` 或空白；
- `content_truncated`：`finish_reason` 显示输出被长度截断，交给内容解析/repair，不当作成功。

前四类都是本次请求未获得可用模型文本，对用户保持 `AI_UPSTREAM_ERROR`，但改为 `retryable=true`，并纳入现有传输重试和调用预算。内部诊断名只进入结构化日志和测试，不持久化原始响应。

### 3.3 内容与领域层

只有在 Adapter 已获得非空文本后，才进入现有 JSON 提取、Zod、语义门和一次 repair。修复后仍不合法继续返回 `INVALID_MODEL_OUTPUT` 且允许用户明确手动重试；不把它误分类为 Provider envelope 故障。

## 4. 调用预算与重试决策

M6.5 不扩大现有 `MAX_UPSTREAM_CALLS_PER_REQUEST = 4` 硬上限。初始调用、传输/响应重试和模型 repair 全部共享同一计数器：

```text
最常见成功：1 次上游调用
临时响应异常：最多 1 次初始 + 2 次自动重试
合法文本但场景契约错误：1 次初始 + 1 次 repair
重试后又需要 repair：总数仍不得超过 4
```

自动重试采用短指数退避与 jitter，每次等待前和发起前都检查 AbortSignal。不在 Adapter 和 pipeline 同时各自重试；Adapter 只负责分类，pipeline 是唯一的预算与重试决策者。

## 5. 实施分解

### M6.5.0：冻结故障样本与诊断契约

先在 Adapter 单元测试中补全脱敏 fixture：正常 DeepSeek envelope、空响应体、非 JSON、缺 `choices`、空 `content`、`finish_reason=length`、429、502、401 和 AbortError。固定期望的 error code、retryable 和内部诊断名，不使用真实 Prompt 或响应原文作为 fixture。

**退出门**：每一种远端失败都有确定的自动重试决策，现有正常响应测试保持通过。

### M6.5.1：重构 OpenAI-compatible 响应解码

将 Adapter 拆成“HTTP 状态映射、响应文本读取、JSON 解析、envelope 验证、统一结果装配”五步。新增内部诊断字段，但不将 raw body 放入 Error、API 响应、MySQL 或日志。

**退出门**：HTTP 2xx 空体/非 JSON/envelope 异常/空内容不再被标记为不可重试；401/403 仍明确不可重试。

### M6.5.2：接入受限重试、预算和安全日志

让 outline/scene pipeline 对新响应分类复用现有传输重试，验证调用上限、退避、取消和 repair 不会叠加失控。结构化日志增加 `providerStatus`、`responseKind`、`contentType`、`responseBytes`、`finishReason`、`upstreamAttempt`、`willRetry` 和 `retryDelayMs`；不记录响应体、Prompt、主题、Key 或 URL 凭据。

**退出门**：注入“首次空内容、第二次正常”时自动恢复；连续异常时在硬上限内结束；取消后不会再发起请求。

### M6.5.3：改善生成页恢复反馈

保留现有逐场状态和局部失败隔离，只改善展示语义：自动重试时显示当前尝试和已等待时间；远端响应耗尽重试后显示“可手动重试”和 `requestId`；只有认证/配置/明确请求不兼容才显示“需修正配置”。

本阶段不将每个内部诊断细节暴露给普通用户，也不会让前端自己发起一套独立的隐式重试。

**退出门**：用户能区分“系统正在恢复、可手动重试、必须修正配置”；失败场景右侧始终有与错误分类一致的操作。

### M6.5.4：自动回归与 DeepSeek 受控验收

增加 Adapter 单元测试、pipeline 预算/取消测试、API error envelope 测试和浏览器故障注入。mock 需要确定性模拟“首次 2xx 空响应，后续恢复”与“连续异常后手动重试”。最后用真实 DeepSeek 生成一门 3～5 场景课程，记录模型、时间、完成数、每场景上游调用数、自动重试数、repair 数和 requestId，不保存 Key 或原始响应。

**退出门**：`pnpm verify:full` 通过；故障注入证明可恢复异常能自动或手动恢复；不可恢复配置错误不重试；DeepSeek smoke 在调用硬上限内完成或以正确的可恢复状态失败。

### 6.2 验收后缺陷回归：JSX 只读边界与部分课堂预览

2026-08-26 对真实失败课程复盘发现，React 教学场景在 `code.code` 中生成 JSX 标签后，被旧版 `containsForbiddenMarkup(JSON.stringify(output))` 当作可执行 HTML 拒绝；原响应和一次 repair 都保留教学源码，因此每次请求最终都是 `INVALID_MODEL_OUTPUT`。这不是 DeepSeek 传输或 envelope 异常，也不应通过增加自动重试次数解决。

修复将安全门收窄到真正作为普通文本显示的字段：标题、讲解、摘要、段落、列表、提示块、题目和 caption 继续禁止 HTML 与外链；`code.code` 允许 HTML/JSX/TSX 源码，因为固定 `SlideRenderer` 只把它放入 `<pre><code>` 并由 React 转义，不使用 `dangerouslySetInnerHTML` 或执行器。slide Prompt 与 repair Prompt 同步声明这一责任边界。

同一回归补齐了既有 FR-209：Course 只要保存了一个 Scene 就能进入课堂的部分预览，页面明确显示完成数、原始场景序号和返回生成页入口；`Course.status=ready` 仍严格要求所有场景 ready。该修复不改变后续质量、画布、互动和修订计划，也不把部分预览当作整课完成。

新增 JSX 校验与 partial classroom 渲染两项测试后，`pnpm verify:full` 通过：15 个文件、64 项单元测试，1 个文件、9 项 MySQL 集成测试，production build 与 Chromium E2E 1/1 均成功。

## 7. 明确不做

M6.5 不修改 Prompt v1 的教学策略，不增加 CourseBrief、schemaVersion 2、Slide/PPTElement、interactive/diagram、单场景意见再生成、LLM-as-judge、LangGraph、多智能体、RAG 或多模态。不引入百炼验收、双 Provider 路由、异机部署或后台任务队列。

## 8. 推荐提交顺序

1. `test(ai): 冻结远端响应异常 fixture 与分类契约`
2. `fix(ai): 分层解码 OpenAI-compatible 响应`
3. `fix(generation): 将可恢复响应纳入受限重试和调用预算`
4. `feat(ui): 展示远端恢复进度和一致的手动重试入口`
5. `test(docs): 完成 M6.5 回归、DeepSeek smoke 与验收证据`

## 9. 与 M7～M10 的衔接

M6.5 完成后，下一步仍是 [09-v0.4 课程质量、幻灯片与互动开发方案](09-v0.4-quality-and-interaction-plan.md) 中已经定义并保留历史名称的 M7.0。后续路线已在 M6.5 完成后重新分段为 M7.0/M7.1 课程质量基础、M8 PPT 式只读幻灯片画布、M9 diagram 互动和 M10 单场景再生成与 v0.4 验收；M11 简化资源包导出与 M12 编辑器可选。M6.5 只为这些阶段提供稳定的 Provider 边界，不改变其安全边界和验收范围。
